# Observable and resumable outer-loop harness (design)

Date: 2026-06-19. Status: approved, pending spec review.

## Motivation

The first GPU outer-loop run (2026-06-18, recorded in
`experiments/results/expert_iteration_rounds.md`) ran 14.7 hours and
produced exactly three summary lines. It had no intermediate progress
output, no checkpoint, no resumability, and no provenance beyond a
hand-redirected log. The `L_Q` vs `L_pi` split and the prior-sharpening
signal were never persisted, so two of the signals the handoff asked to
read could not be read at all. A crash at hour 14 would have lost
everything.

This retrofit makes a long outer-loop run observable (periodic flushed
output, persisted metrics), recoverable (checkpoint and resume), and
reproducible (a unique run directory with full metadata). It is a standing
requirement for any simulation in this project, not a one-off.

## Scope and non-goals

In scope: instrumentation, persistence, and provenance around the existing
outer loop.

Explicitly NOT in scope (the learning algorithm is untouched):

- no change to the losses (`train.py`), MCTS (`mcts.py`), the replay
  buffer semantics (`replay.py`), or the heads (`architecture.py`)
- no W&B, TensorBoard, or trackio (plain JSONL plus a text log matches the
  repository's existing experiment style: `b_sweep_analyze.py`,
  `collect_distillation.py`, the `load_jsonl` helpers)
- no multi-GPU, no distributed training, no async log writers

## Architecture

Two layers, mirroring the existing split between the tested core
(`src/verifier_anchored_rl/outer_loop.py`) and the GPU harness
(`experiments/run_outer_loop.py`).

### Layer 1: outer_loop.py (tested core), additive hooks

The public functions keep their current signatures; every new parameter is
optional with a default that reproduces today's behavior, so the existing
tests and the byte-for-byte CPU path are unchanged.

- `collect_iteration` gains an optional `on_decision(info: dict)` callback,
  fired once per completed MCTS decision. `info` carries: iteration,
  problem index, turn, chosen verb, the `pi_MCTS` argmax and its
  probability, the chosen verb's `q_MCTS`, the encoder's cumulative
  prefill/gen call and token counters, and elapsed seconds. The existing
  `record_sink` (per-record streaming) is retained.
- `collect_iteration` gains an optional `on_trajectory_end(state)` callback,
  fired after each problem trajectory completes, carrying enough state for
  the harness to write a checkpoint at that boundary (see Resume).
- `run_outer_loop` gains optional `on_train_step(info: dict)` (fired every
  `log_every` steps with `L_Q`, `L_pi`, `L_total`, global step),
  `on_iteration_end(stats: IterationStats)`, and `save_checkpoint(state:
  dict)` callbacks, plus a `resume_state: dict | None` parameter.
- `IterationStats` gains the loss split: `q_first`, `q_last`, `q_mean`,
  `pi_first`, `pi_last`, `pi_mean` (in addition to the existing
  `total`-derived first/last). The data already exists in the per-step
  `losses` list that `train_step` returns; today it is discarded.

### Layer 2: run_outer_loop.py (harness)

Responsibilities: build the run directory, gather and write metadata, wire
the callbacks to a flushed logger and the JSONL/checkpoint writers, and
implement `--resume`.

## Run directory layout

`experiments/results/runs/<UTC-timestamp>-<git-sha8>[-<tag>]/`

(The timestamp is generated by the harness with `datetime.now(timezone.utc)`;
this is a normal Python script, so that is allowed.)

- `metadata.json`: argparse args, git SHA and a dirty flag, hostname, GPU
  name and driver, torch / transformers / CUDA / Python versions, model id,
  dtype and device, seeds, start time, end time, and final status
  (`running` / `completed` / `failed`). Written at start (status
  `running`), updated at end.
- `progress.log`: human-readable, line-buffered, tee'd to stdout. One line
  per decision and one line per `log_every` train steps. Includes a
  running ETA once the first iteration's timing is known.
- `records.jsonl`: one collected distillation record per line (the exact
  `collect_distillation` schema), streamed as produced via `record_sink`.
- `metrics.jsonl`: one JSON object per completed iteration: iteration,
  decisions, sims, buffer size, prefill/gen calls and tokens, the loss
  split (`L_Q`, `L_pi`, `L_total` first/last/mean), and wall-clock seconds.
- `checkpoint.pt`: written atomically (write to `checkpoint.pt.tmp`, then
  `os.replace`). Contents below.
- `summary.md`: the human summary table, rewritten after each iteration so
  a crash still leaves a partial, readable summary.

## Checkpoint contents and resume

Checkpoint is a single dict saved with `torch.save`, loaded with
`torch.load(..., map_location="cpu")` (following the existing
`trained_prior.load_actor_from_checkpoint` pattern, though this checkpoint
also stores optimizer and buffer state, so it is not `weights_only`):

```
{
  "phase": "collecting" | "training",
  "iteration": int,                      # 1-based index of the current iteration
  "problems_done_this_iter": int,        # trajectories completed this iteration
  "actor_state": actor.state_dict(),
  "optimizer_state": optimizer.state_dict(),
  "buffer": <serialized ReplayBuffer samples + priorities>,
  "global_step": int,                    # trainer step count (drives target sync)
  "numpy_rng_state": rng.bit_generator.state,
  "config": <the run config dict>,
}
```

Checkpoint cadence:

- after each completed problem trajectory during collection (4 problems per
  iteration by default, so a crash loses at most one trajectory, not the
  whole multi-hour iteration), with `phase="collecting"` and the updated
  `problems_done_this_iter`
- after training completes for the iteration, with `phase="training"` and
  `iteration` advanced

`--resume <run-dir>` reloads `checkpoint.pt`, restores the actor, optimizer,
buffer, numpy RNG, and `global_step`, rebuilds the frozen model and encoder
fresh (they are stateless), and continues from the saved `phase` and
position: if `phase="collecting"`, it finishes the remaining trajectories of
`iteration` then trains; if `phase="training"`, it starts the next
iteration. New `records.jsonl`, `metrics.jsonl`, and `progress.log` lines
are appended to the existing run directory.

Determinism note: exact reproduction across a resume requires that the
restored numpy RNG and the frozen weights fully determine subsequent
trajectories. The frozen model is deterministic per seeded call (verified in
the transformers smoke); the numpy RNG drives both MCTS action selection and
the next-verb sampling. Restoring it is therefore sufficient for the CPU
fake-encoder determinism test; on the real GPU a small compute-order
nondeterminism floor exists (documented in the B-sweep sections) and resume
is expected to match the uninterrupted run only up to that floor.

## Testing

TDD with the CPU `FakeEncoder` (no GPU, no model):

1. `on_decision` fires once per decision with the documented keys; the loss
   split appears in `on_train_step` payloads.
2. `IterationStats` carries `q_*` and `pi_*` fields consistent with the
   per-step losses.
3. Checkpoint round-trip: save then load reproduces actor weights, buffer
   contents and priorities, numpy RNG state, and `global_step` exactly.
4. Load-bearing resume test: an uninterrupted N-iteration run and a run
   stopped after iteration 1 then resumed from its checkpoint produce
   identical final actor weights and identical buffer contents (fixed seed,
   restored RNG). This is the analogue of the existing loop-closes test and
   is the proof the resume contract is correct.
5. Harness unit tests: run directory is created with the documented files;
   `metadata.json` has the required keys; `metrics.jsonl` gets one line per
   iteration; atomic checkpoint write leaves no `.tmp` file on success.

Then a short real-GPU smoke (`--iterations 1 --num-simulations 8 --problems
multiply_small`, about 10 to 20 minutes): confirm progress lines stream to
`progress.log` during collection, a checkpoint appears after the trajectory,
metrics carry the `L_Q`/`L_pi` split, and a `--resume` of that run directory
continues and completes without error on bf16/CUDA.

## Risks

- Checkpoint serialization of the replay buffer must round-trip the tensors
  and the numpy priority array; covered by test 3.
- Writing a checkpoint every trajectory adds I/O during collection, but the
  actor is under 1M parameters and the buffer is small (tens to low
  thousands of samples), so the write is cheap relative to a multi-second
  generation. Atomic write avoids a torn checkpoint on crash.
- Appending to JSONL/log on resume must not corrupt earlier content; open in
  append mode, never truncate an existing run directory.
